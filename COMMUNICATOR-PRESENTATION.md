# Full-screen Fellowship Communicator

This development pass starts from merged NextPhase commit `01d91189b59e66d3e17b753e3c2b3841416d54d2` on `feature/fullscreen-communicator`. It supersedes the floating presentation in MODELESS-CONVERSATION.md; the existing Firebase services, message schema, rules, authorization and page-memory session model remain unchanged.

## Two presentations

- **Full screen:** the one communication surface fills the available application/visual viewport on mobile and desktop. Its list and active conversation remain views of the same surface. There is no floating-width layout, drag grip, expand/reduce control or competing HomeGroups header/dock.
- **Sideparked:** the same persistent 44px edge arrow restores the current list/chat view. The header's outward arrow and Escape sidepark it. Existing Alt+Left/Right shortcuts select the parked side. These are the only presentation modes, `fullscreen` and `minimized`; compatibility cleanup APIs do not introduce a third visible state.
- Workspace content, Orbit and other body-level surfaces are temporarily hidden and inert while full screen, without unmounting them or pausing audio. Original inert state is restored on sideparking; late-mounted background surfaces are covered too. Keyboard focus stays inside the full-screen surface. Reduced-motion preference skips the short opening/parking animation.
- Opening a message's Scripture reference sideparks the Communicator and uses the existing reader/history architecture. Closing the reader stack restores the full-screen conversation. Workspace and unfinished drafts remain intact. Contextual sharing prepares a reference for review; sending still uses the existing authorized write operation.

## Presentation

The Theme Manager's centralized communication roles provide midnight-blue surfaces, slate incoming bubbles, blue/teal outgoing bubbles and restrained green actions. Static cyan/emerald depth gradients, a fine illuminated upper edge and inset avatar highlights give the full-screen canvas depth without a background download, continuous animation or expensive blur. Existing light and diagnostic palettes remain supported. Native system typography, a compact contextual header, initials and privacy labels, comfortable touch targets and a keyboard-sized composer replace the nested floating frame. Desktop content has a readable measure within a full-screen background, not a centered floating card. The list does not invent message previews, unread counts, presence, read receipts or participation. No new network font or UI dependency is introduced.

The Fellowship Navigator's map, communities, flip and workspace navigation are preserved. Users uncover them by sideparking. The original media session, account isolation, immutable saved messages, supported newest-50-message behavior and per-account/per-conversation drafts remain in their existing components. Drafts are still page-memory only; reload, sign-out and cross-device recovery have not been added.

## Attachment-panel correction after physical iPhone review

The reported vertical labels and missing composer were reproduced against `503f423d` in the actual DOM at 375 × 481. The element is `.conversation-attachment-panel`, but its positioning rule targeted `.communication-attachment-panel`. Without that rule, the panel remained in normal flow inside the 44px + grid column. Its width was 44px and the composer grew to 596.75px, beyond the available screen. This is a selector/containing-block defect, not an established Safari engine fault.

The corrected panel is positioned above the composer, spans its available width and uses a single `minmax(0, 1fr)` action column. Long passage labels wrap as normal lines. Its maximum height follows the actual gap between the existing full-screen header and composer; overflow scrolls inside the tray. The composer remains one row while the tray is open, retaining the complete multiline draft. Its normal expanded height is also capped by the conversation's available space. The duplicate attachment-preview chip is temporarily hidden while that reference is editable in the tray, then returns on closing. Focusing the reference input scrolls only the tray as necessary. Resize/visual-viewport listeners and a ResizeObserver recalculate this local layout and are removed on discussion teardown. The application's viewport model and two presentation states are unchanged.

At 375 × 481, the corrected tray measured 351px wide, its two actions each 44px high, and the reply remained inside the screen. The new regression exercises the original Genesis 32:4–32:13 label, a longer 1 Thessalonians 4:13–5:11 reference, 320/375px widths, 240/260/300px keyboard-sized heights, a visual-only viewport reduction with a 40px pan offset, internal scrolling and focused-input visibility, repeated toggle/Escape/select, external sharing without sending, an existing attachment and a multiline unsent reply. It also covers a desktop attachment tray. The first extended run exposed reference-input clipping in a very short tray; the inner-scroll correction addresses it. A separate test wait used an Arabic numeral where this KJV corpus renders the book's Roman numeral; only that test expectation was corrected.

Validation: the focused Communicator regression, existing viewport regression, JavaScript syntax checks and session-isolation checks passed using synthetic identities. Measurements and phone captures are retained under ignored `.pilot-tmp/` on F:. These checks simulate keyboard/toolbars and do not establish physical Safari behavior. Before a future approved preview update is accepted, verify + opening/closing, long labels, reference-field focus, keyboard dismissal, toolbar changes, deliberate attachment selection and the accessible composer on the actual iPhone. ## Keyboard blackout — release remains blocked pending device verification

The owner reported that opening the keyboard in the installed Home Screen app makes the web content black; dismissing it restores the view. The earlier keyboard-size fixture did not move the root document and was insufficient coverage. There is no physical iPhone/Safari execution environment attached to this workstation, so neither that report nor the correction is labeled device-verified.

Before applying the correction, a focused real-DOM reproduction against `3cc568b` exercised an editor-focused document scroll plus positive visual-viewport offset. The hidden workspace's rectangle became y=-300, height=540, bottom=240. `workspaceRect()` intersected it with a visible viewport starting at y=300 and produced height=0. The Communicator remained `fullscreen`, `hidden=false`, `inert=false`, while the background stayed `visibility:hidden`. A captured all-black frame and failing assertion are retained as `.pilot-tmp/communicator-keyboard-before.log` and `communicator-fullscreen/10-keyboard-document-pan-before.png`. This establishes a deterministic application defect with the reported symptom. It does not establish that the device produced those exact metrics; the phone-specific causal path is still a hypothesis until captured or physically verified.

The full-screen communication surface now uses its own visible-viewport dimensions and a single absolute document-coordinate layer. `pageTop`/`pageLeft` (or scroll plus viewport offset) locate that layer; its child fills it. Its size retains the existing small-viewport/toolbar cap using the workspace's layout dimensions, not an intersection with its focus-panned screen rectangle. The nested fixed/contained positioning chain is removed. Zero-size transient viewport readings retain the last valid layout. Focus and pageshow request layout updates without changing presentation state, hiding the surface, clearing drafts or remounting audio. The wrapper leaves layout at the end of the existing parking animation, preventing its retained dimensions from causing horizontal overflow after a parked resize. Existing workspace, reader and Orbit parking geometry, viewport meta policy and safe-area treatment are unchanged. With identical reproduction inputs the Communicator is 240px high instead of 0px.

The regression covers document scroll plus visual pan, visual-only pan with an unscrolled document, a separately displaced covered workspace, page-offset fallback, a zero-height transient, attachment-field focus/internal scrolling, usable header/messages/reply/send target, dismissal, sidepark/restore, retained draft/reference and continued playback of the same real audio element. It uses Chromium and synthetic identities, not the iOS keyboard engine. The regular conversation journey also remains required for review/send, reader return, account isolation and denied access.

The focused Communicator run passed those geometry checks plus the existing attachment, conversation, reader-return and privacy contracts; syntax and session-isolation checks passed too. A later fixture review caught an inconsistent event simulation: it replaced the visualViewport object and dispatched subsequent events only on that replacement, while production listeners correctly remained on the original object. Fixture transitions now also dispatch the real window resize path, rather than relying on a coincidental scroll event. Failed attempts are retained rather than counted as passes. Physical keyboard behavior remains unverified, and passing automated checks are not evidence that the real-device failure is resolved.

Final validation after the wrapper correction: the existing viewport suite and complete focused Communicator suite passed; the opt-in trace-copy check, syntax checks and session-isolation check also passed. The wrapper is width-capped during transitions and hidden after parking. Logs are `.pilot-tmp/communicator-keyboard-{regression,viewport,diagnostics}.log`; no live family account or production write was used.

For physical investigation only, `layout=check` adds a compact Copy layout control within the Communicator. Its local, bounded 40-sample trace includes viewport/page offsets, rectangles, visibility/presentation flags and focused element type. It includes no message bodies, drafts, names, account identifiers or tokens, sends nothing over the network and is not persisted. `layoutDetails()` also reports iOS's standalone flag. If the next pilot still blacks out, dismiss the keyboard and copy this trace from the same session before refreshing.

Physical acceptance remains mandatory in **both** an ordinary Safari tab and the installed Home Screen app on the fresh build: open a saved conversation, type and send, open + and edit/select a long Scripture reference with keyboard present, dismiss/reopen the keyboard, sidepark/reopen, follow a passage and return with an unsent reply, and confirm Orbit playback continues. Preview-channel updates are authorized for this review; no production deployment, merge or Firebase rule/authentication/data change is authorized.

Research context (not proof of this device's cause): [WebKit report 311821](https://bugs.webkit.org/show_bug.cgi?id=311821) describes keyboard panning despite zero reported document scrolling; [VisualViewport](https://developer.mozilla.org/en-US/docs/Web/API/VisualViewport) distinguishes the visible viewport and its page coordinates. The correction targets the reproduced HomeGroups dependency on the moved background, rather than assuming all iOS keyboard failures share one engine bug.
